# Build SpaceNotes Live on a simple log

SpaceNotes Live should be built from two parts. The first is a small **room server that SpaceNotes owns**. It keeps an ordered list of drawing changes, and the stroke data in that list is the same `PortableStroke` JSON the app already stores. The second is **LiveKit**, an open-source video service, which carries the cameras and microphones. Everything should be packaged as a separate plugin: one Swift package, one Android library and one web package, all checked against shared test files, in the same way TeachDraw plugs into the notebook. Nobody else sells what this would be. GoodNotes has live shared documents but no call, and they need a paid Pro plan. Notability's live sync was still "coming soon" in January 2026. Students who want to study together on a call fall back on screen-sharing an iPad into Zoom, and then only one person can write. The ink is cheap to run, well under ₹0.5 per student-hour. Video is the whole bill: about **₹2.5–4 per student-hour for voice only** and about **₹5–15 per student-hour with cameras**, depending on how small the camera tiles are. So the room should start with voice on and cameras off. Every library suggested for the design has a licence that allows a closed-source app (MIT or Apache-2.0), so none of them repeats the tldraw or AGPL problems this project has already avoided. Before launch, the main open questions are a few LiveKit prices that could not be confirmed, and legal advice on students under 18 under India's data-protection rules, whose consent duties start on 13 May 2027.

## No one offers a call around your own annotated notebook

The idea is to open a lecture PDF you have already written on, tap once, and have friends join by voice. Everyone sees the same page, and each stroke appears as it is drawn. The research found no app that does this.

The notebook apps sync slowly or charge for it. For GoodNotes' older shared-document model, the help centre says changes appear "as soon as you finish an edit, for example by lifting your stylus", so others see whole words at a time, not a moving pen ([GoodNotes Support](https://support.goodnotes.com/hc/en-us/articles/7353695997839-Share-a-document-for-collaboration)). GoodNotes has since added "Live Cursor" and near-instant updates for **up to 50 people**. A live session cannot start, though, until someone with a **Pro subscription** ($35.99 a year) opens the document ([GoodNotes Live Cursor](https://support.goodnotes.com/hc/en-us/articles/13922131401615-Real-time-Collaboration-with-Live-Cursor-in-shared-documents), [TechCrunch](https://techcrunch.com/2025/09/23/goodnotes-collaborative-docs-and-ai-assitant-to-cater-to-professional-users/)). Notability's January 2026 post still listed "Shared Notes with Real-Time Sync" as **coming soon** ([Notability blog](https://blog.notability.com/post/whats-coming-to-notability-this-semester)). One OneNote user said their friend waited **"at least 10 seconds"** to see any writing, while Microsoft Whiteboard "synced instantly" ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/5197275/onenote-sync-is-very-slow-when-collaborating-with)). Samsung Notes allows live editing for up to 10 people, but only on Galaxy devices, and it has no view-only role ([Samsung support](https://www.samsung.com/us/support/answer/ANS10003702/)).

The whiteboard apps are fast and have good group features, but they start from a blank board, not from the student's own slides. FigJam's "Spotlight" and Miro's "Bring everyone to me" let a leader make everyone's screen follow theirs. In Miro, following ends as soon as a person moves on their own, which is a gentle rule worth copying ([Miro Help](https://help.miro.com/hc/en-us/articles/360013358479-Attention-management), [Figma Help](https://help.figma.com/hc/en-us/articles/5025214483351-Facilitate-meetings-with-spotlight)). Teams and Zoom let the host switch the board between "everyone can edit" and "view only" ([Zoom Support](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0058153)). Google's Jamboard, once Meet's built-in whiteboard, closed on **31 December 2024** ([Google Workspace Updates](https://workspaceupdates.googleblog.com/2023/09/the-next-phase-of-digital-whiteboarding-for-google-workspace.html)). The usual workaround is screen-sharing GoodNotes into Zoom, where only the presenter can write ([Northeastern AAC](https://asianamericancenter.northeastern.edu/blog/good-notes/)).

That leaves a clear gap. SpaceNotes Live would combine voice or video, a page that follows the host, ink that appears as it is drawn, simple host controls (host only, everyone draws, pass the pen), and joining from iPad, Android or a web browser. It would not need a subscription for every friend. One caution: the research could not reach Reddit, so what students actually want here is inferred from product gaps rather than taken from their own words. A short survey of real users is worth doing before phase 3.

## Ink needs an ordered log on a server, not a CRDT library

There are two main ways to keep several copies of a drawing the same. A **CRDT** ("conflict-free replicated data type") is a clever data format that lets every device merge changes without a central referee. The main open-source ones are Yjs, Automerge and Loro. A **server-authoritative op log** works differently. Each change ("operation", or "op") goes to one server. The server numbers the ops in order and sends them to everyone, and when two people change the same thing, the change that reaches the server last wins. This rule is called **last-writer-wins**.

Figma, the biggest shared-canvas product, uses the second approach. It keeps "the latest value that any client has sent for a given property on a given object". It skipped full CRDTs because, with a central server, it could use "a faster and leaner implementation" ([Figma blog](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). Excalidraw gives each shape a version number and marks deleted shapes with a flag rather than removing them, a marker called a **tombstone**. It accepts some "jankiness" in the rare case where two people edit the same shape ([Excalidraw blog](https://plus.excalidraw.com/blog/building-excalidraw-p2p-collaboration-feature)). tldraw built its own server-authoritative sync ([tldraw docs](https://tldraw.dev/docs/sync)).

Ink suits this approach even better than shapes do, because a finished stroke never changes. Drawing is an "add stroke" op. Erasing is a tombstone. Moving with the lasso is a last-writer-wins change to the stroke's position. Two friends drawing at the same moment never clash, because each stroke has its own ID.

The CRDT libraries have safe licences. Yjs, Automerge and Loro are all **MIT**, which allows closed-source use ([y-crdt licence](https://raw.githubusercontent.com/y-crdt/y-crdt/main/LICENSE), [Loro](https://github.com/loro-dev/loro)). They fail on Android. Yjs's Kotlin port says it is "currently not active" ([ykt](https://github.com/y-crdt/ykt)), and its Swift port is marked "WIP" ([y-uniffi](https://github.com/y-crdt/y-uniffi)). Automerge's Java/Android wrapper is still at version **0.0.x** ([automerge-java](https://github.com/automerge/automerge-java)). Loro, the most active of the three, has official Swift support but **no Kotlin binding** ([loro-ffi](https://github.com/loro-dev/loro-ffi)). On the web, Loro and Automerge each add a download of **3.3–3.6 MB** ([npm loro-crdt](https://registry.npmjs.org/loro-crdt), [npm Automerge](https://registry.npmjs.org/@automerge/automerge)).

There is also a deeper reason to avoid a CRDT. It would become the real record of the page, and `PortableStroke` would become a copy made from it. That reverses the project's rule that the app-owned, portable JSON model is the source of truth. With an op log, the ops simply carry `PortableStroke` JSON.

The code to avoid is still tldraw's and PenEcho's. tldraw's sync engine is free only for non-commercial use ([tldraw announcement](https://tldraw.substack.com/p/announcing-tldraw-sync)). Its ideas may be borrowed; its code may not. The log proposed here is written in-house, so it carries no licence risk at all.

The log handles the awkward cases with simple rules. **Undo** removes only your own work: undoing a stroke sends a tombstone for it, and it never touches a friend's strokes. Figma follows the same rule, that undo must not destroy other people's later work ([Figma blog](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). If one person erases a stroke while another moves it, **the erase wins**, because a scribble coming back after you erased it would feel broken. Each op's ID includes the sender's device ID, so a phone that resends after a dropped connection cannot create duplicates.

A **late joiner** first receives a **snapshot**, meaning the whole page as it stands, and then every op numbered after it. This is how tldraw restores its rooms ([tldraw docs](https://tldraw.dev/docs/sync)). A device coming back online sends the last number it saw and receives what it missed, then sends its own queued ops.

To make drawing look live, the room uses **two lanes**. A fast, throwaway lane sends the points of a stroke in progress about 20–30 times a second. tldraw sends updates at **30 frames a second** while people are collaborating ([tldraw collaboration docs](https://tldraw.dev/sdk-features/collaboration)). A permanent lane sends the finished `PortableStroke` once, when the pencil lifts. By the research's own rough estimate (not a measurement), one person drawing needs about **1.5–2 KB a second** if the points are packed compactly, or 10–20 KB a second in plain JSON. Both are tiny next to video. Only the preview is rounded to save space; the saved stroke keeps full precision. If a user needs shared rich text inside text boxes later, that is the one place a CRDT could be reconsidered. Until then, text boxes can follow last-writer-wins like everything else.

## LiveKit carries voice and video at the lowest price

The cameras and microphones should go through an **SFU**, a "selective forwarding unit": a server that receives each person's video once and forwards copies to the others, without mixing them. It uses **WebRTC**, the standard technology for live audio and video in browsers and apps. The research recommends **LiveKit**. Among the options compared, it is the only one with its own SDKs (ready-made code libraries) for Swift, Android with Jetpack Compose, and the web. Its server is open source and can be hosted yourself, and it also runs as a paid cloud service with an **India region** ([LiveKit components-android](https://github.com/livekit/components-android), [LiveKit region pinning](https://docs.livekit.io/deploy/admin/regions/region-pinning/)).

LiveKit Cloud's "Ship" plan costs **$50 a month** for 150,000 participant-minutes, then **$0.0005 a minute**. The "Scale" plan costs $500 a month, then $0.0004 a minute, with 3 TB of data included and **$0.10 per GB** after that ([LiveKit pricing](https://livekit.com/pricing)). Most rivals charge four to eight times more per minute. Daily charges $0.0015–0.004 per video participant-minute ([Daily pricing](https://www.daily.co/pricing/video-sdk/)). Agora charges $3.99 per 1,000 HD minutes ([Agora pricing](https://docs.agora.io/en/video-calling/overview/pricing)). Cloudflare's RealtimeKit will charge $0.002 a minute once it leaves beta ([Cloudflare](https://developers.cloudflare.com/realtime/realtimekit/pricing)). 100ms, an Indian company, charges $0.004 a minute ([100ms pricing](https://www.100ms.live/pricing)).

Cloudflare's basic SFU is cheaper still, at $0.05 per GB, but the team would then have to build the room logic on all three platforms itself. mediasoup has no official iPad or Android SDKs. Jitsi's hosted service puts its own full meeting screen inside the app, which clashes with a custom notebook view.

Licences fit a closed-source app. LiveKit's Android components are Apache-2.0 ([GitHub](https://github.com/livekit/components-android)). The notes say the server is also Apache-2.0, but that is from memory and should be confirmed on its GitHub page. Agora and Zoom's SDKs are proprietary, and they offer no way to host the service yourself.

LiveKit also cannot run on Cloud Run, the service that hosts the current proxy. It needs open network ports on a real server, and its docs say it does not support "serverless and/or private clusters" ([LiveKit Kubernetes](https://docs.livekit.io/home/self-hosting/kubernetes/)). That is why the plan starts on LiveKit Cloud, with self-hosting on a Google Compute Engine machine in Mumbai as a later option. The research found little saving in self-hosting until video traffic passes about 10 TB a month, because Google's own charge for outgoing data, **$0.085–0.12 per GB**, is close to LiveKit's ([GCP network pricing](https://cloud.google.com/network-tiers/pricing)).

## How the pieces fit together

The room server is a new, small Node service on Cloud Run in Mumbai (asia-south1). It should be kept separate from `gemini-proxy`, because long-lived connections would keep that service's instances running. Devices connect to it over a **WebSocket**, a connection that stays open so messages can flow both ways at any time. The existing proxy already relays one for live voice.

Cloud Run has three limits the design must respect. A WebSocket is cut after at most **60 minutes**, so the app must reconnect and resume without the student noticing. The service is billed the whole time any socket is open. And Google only "best effort" keeps a room's members on the same machine ([Cloud Run WebSockets](https://docs.cloud.google.com/run/docs/triggering/websockets)). The simplest start is to run a **single instance**. It can hold about 1,000 connections, which is roughly **160 six-person rooms** ([Cloud Run WebSockets](https://docs.cloud.google.com/run/docs/triggering/websockets)). Beyond that, Google's recommended fix is Redis pub/sub, a shared message board between instances.

Firestore, Firebase's database, is the wrong place for strokes. It allows about **one write per second per document** ([Firebase best practices](https://firebase.google.com/docs/firestore/best-practices)), and streaming ink through it would cost an estimated **₹12–50 per room-hour**, against about ₹0.1 for the relay. Firestore should hold only the room's details: host, code, members and locks.

Storage has three layers. The live log sits in the server's memory. Every few hundred ops, or every 30 seconds, a compressed chunk is saved to a Cloud Storage bucket in Mumbai, together with regular page snapshots in the existing `PortablePage` format. When the room closes, the result is written into the host's notebook.

Joining reuses the app's sign-in. Every connection carries a **Firebase ID token**, a short-lived signed pass proving who the user is, and the server checks it, as the proxy already does. Friends without an account join as anonymous users, which the project already allows, if the host permits guests. The host creates a room and gets a **six-character code**. The code avoids look-alike characters such as 0, O, 1 and I, expires within a day, and is rate-limited so it cannot be guessed. The host also gets a link that opens the app on iPad (Universal Links) or Android (App Links), or a web page if the app is not installed.

The proxy also issues each person a LiveKit **JWT**, a signed ticket that says which room they may enter and whether they may speak or show video. LiveKit's docs say these tickets must be made on a server ([LiveKit authentication](https://docs.livekit.io/home/get-started/authentication/)). The LiveKit secret sits in Secret Manager with the other keys.

Host powers are enforced on the server, not trusted to each device. Before forwarding any op, the room server checks the sender's role and the lock state. "Remove" closes that person's connection and asks LiveKit to drop them from the call. This is also why ink should not travel only over LiveKit's built-in data messages, which are otherwise capable (reliable messages up to 15 KiB, fast ones up to 1,300 bytes, [LiveKit data packets](https://docs.livekit.io/home/client/data/packets/)). With LiveKit's messages alone, there would be no numbered log, nothing for late joiners and no way to enforce a drawing lock.

The plugin follows the TeachDraw pattern. It gets its own repository holding a written protocol specification, versioned from the start, and JSON test files for every message type, which the Swift package, the Android library and the npm package must all read and write identically, as `fixtures/notebook-format/` already requires of the notebook model. The same repository holds the three client packages, with video kept as a separate, optional part, and the Node server. The notebook app supplies three things: a sign-in token, an adapter that turns its strokes into `PortableStroke` and back, and places in its screens for the plugin's views. So the plugin never needs to know the notebook's internals.

## Video bandwidth, not ink, sets the price

A 6-person room at 360p video downloads about **1 GB per person per hour**. The same room with voice only uses about 0.07 GB. Small 180p tiles, with LiveKit sending each viewer only the quality it needs (**simulcast** plus "adaptive stream"), cut video to about 0.34 GB ([LiveKit video presets](https://raw.githubusercontent.com/livekit/client-sdk-js/main/src/room/track/options.ts), [LiveKit advanced tracks](https://docs.livekit.io/home/client/tracks/advanced/)). The notes' worked estimates use LiveKit's list prices ([LiveKit pricing](https://livekit.com/pricing)) and ₹96 to the dollar, and assume each student spends 5 hours a month in rooms:

| Room type | 1,000 students a month | 10,000 students a month | Per student-hour |
|---|---|---|---|
| Voice + shared ink | ~₹20,600 | ~₹1.18 lakh | ₹2.4–4.1 |
| 180p camera tiles + ink | — | ~₹2.5 lakh | ~₹5 |
| 360p cameras + ink | ~₹77,000 | ~₹5.6 lakh | ₹11–15 |
| 360p, self-hosted in Mumbai | ~₹76,000 | ~₹4.8 lakh | ₹9.6–15 |

Against a ₹499 monthly subscription, five hours of voice costs about ₹15 per student, and five hours of 360p video about ₹55–70. That is why the room should open with **cameras off and microphones on**. It should offer a data-saver switch and show only a few video tiles at once. On mobile data this is also kinder to students: at 180p, a 5-person room uses about 330 MB an hour on each phone, against about 43 MB with voice only.

These figures carry real uncertainty. The LiveKit pricing page did not say whether the $50 Ship plan charges for data. The two sets of notes also disagree about the free Build plan, one reading 5,000 minutes with 100 connections and the other 1,000 minutes with 5, so it should be checked before testing at any size. Mumbai prices for Cloud Run and Compute Engine were not found either. A one-week load test and beta usage data should replace these estimates before any price is set.

## Privacy rules bite hardest on minors and recordings

India's **DPDP** (Digital Personal Data Protection) Rules were notified on 13 November 2025. Their consent rules, including **verifiable parental consent for anyone under 18**, apply from **13 May 2027** ([dpdprules.org](https://dpdprules.org/rules/10)). Parents can be verified with details the company already holds, or through government-authorised tokens such as DigiLocker ([dpdpa.com](https://www.dpdpa.com/dpdparules/rule10.html)), and edtech is named as a sector with heavy exposure ([Consently](https://www.consently.in/blog/verifiable-parental-consent-dpdp-rules-2025-edtech-gaming)). Most MBBS students are adults. The app also offers courses such as B.Sc Nursing, and 17-year-old aspirants are likely users, so it should ask for age at signup and switch on a parental-consent path for under-18s.

The notes make three design recommendations here (they are proposals, not legal advice). **Recording** should be off by default. Only the host can start it, and everyone must see a banner and accept or leave. Recordings should be deleted after a set time. Room data should stay in India: the room server, its storage bucket and LiveKit's India region. Media and ink are encrypted as they travel, but the servers can read them. Full end-to-end encryption of ink would stop the server from enforcing locks or building snapshots, so it is not recommended for ink. The research found no source on whether a study call needs its own notice beyond the account's consent, so a lawyer should review the design before launch.

## A four-phase build plan

The plan follows the project's habit of small, shippable steps, each proven end to end before the next.

| Phase | What ships | Proves |
|---|---|---|
| 1. Protocol and ink | New plugin repo; protocol spec and JSON test files; Swift package plus Node room server on Cloud Run (one instance, Mumbai); rooms, codes, links, anonymous guests; two-lane ink; undo of your own strokes; late join and reconnect; host lock and remove. iPad to iPad, plus a web viewer. | Shared ink works, streams live and survives a dropped connection. |
| 2. Voice | LiveKit Cloud (free plan in testing, Ship at launch, India region); token minting in the proxy; voice on by default; named cursors in colours; follow the host's page with a "jump back" chip. | A real study group can talk and draw together. |
| 3. Android and cameras | Kotlin/Compose client passing the same test files; opt-in 180p camera tiles; data saver; pass the pen and raise a hand; usage and cost logging per room. | Mixed iPad and Android groups; the real cost per student-hour. |
| 4. Into the notebook | Vendor the plugin into the notebook with a sync script, like TeachDraw; start a room from any page; the session's ink saved into each notebook; Redis or self-hosted LiveKit only once traffic warrants it. | SpaceNotes Live as a feature of the main app. |

Web joining matters early, because it lets a friend without the app take part. Consent screens and age checks should be in place before public launch, and well before May 2027.

## Conclusion

The hard part of SpaceNotes Live is not the technology. Figma and tldraw have already shown that a central, ordered log beats clever merging libraries for canvases. SpaceNotes also has an advantage those products lacked: its portable stroke format and its cross-platform test files already exist, so the room protocol mostly adds ordering and permissions to data the app already understands. The bigger decisions are about the product and money. Voice-first rooms cost about as much as a cup of tea per student each month, while a camera-heavy design could take a large share of a ₹499 subscription. The pricing decision the owner still owes should therefore settle what Live costs students, and whether only the host pays.

Two things would change this plan. If students turn out to want long, heavily shared typed notes rather than ink, text boxes would need a CRDT, and Kotlin support would become the blocker. If room traffic grows past about 10 TB of video a month, self-hosting LiveKit in Mumbai becomes worth the extra work. Neither is likely at the start.
